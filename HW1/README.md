# پاسخ تمرین Git

> **نکتهٔ نمایش:** برای راست‌چین‌بودن متن فارسی از `dir="rtl"` و
> `align="right"` استفاده شده است. نام دستورها و قطعه‌کدها در بلوک‌های کد
> به‌صورت چپ‌به‌راست نمایش داده می‌شوند. اگر نمایشگر Markdown ویژگی‌های HTML
> و CSS را پشتیبانی نکند، راست‌چین‌بودن و فونت ممکن است متفاوت باشد.

## سؤال ۱: `merge` و `rebase`

هر دو دستور تغییرات یک شاخه را با شاخه‌ای دیگر ترکیب می‌کنند، اما تاریخچهٔ
متفاوتی می‌سازند:

-   **`merge`:** تاریخچهٔ دو شاخه را حفظ می‌کند و معمولاً یک *merge commit*
    می‌سازد؛ اگر شاخهٔ مقصد از قبل شامل شاخهٔ دیگر باشد، ممکن است فقط
    *fast-forward* رخ دهد. برای ادغام شاخهٔ یک قابلیت در `main`، وقتی حفظ
    تاریخچهٔ واقعی همکاری مهم است، انتخاب مناسبی است.
-   **`rebase`:** کامیت‌های شاخهٔ جاری را روی نوک شاخهٔ مقصد دوباره اعمال
    می‌کند و تاریخچه‌ای خطی‌تر می‌سازد؛ شناسهٔ کامیت‌های بازنویسی‌شده تغییر
    می‌کند. برای مرتب‌کردن تاریخچهٔ یک شاخهٔ محلی و شخصی پیش از ادغام مناسب
    است.

نمونهٔ دستورها:

``` bash

git switch main
git merge feature-login


git switch feature-login
git rebase main
```

**دلیل انتخاب:** `merge` تاریخچهٔ شاخه‌ها را حفظ می‌کند و برای شاخه‌های
مشترک معمولاً کم‌خطرتر است. `rebase` تاریخچه را بازنویسی می‌کند؛ بنابراین
نباید بدون هماهنگی، شاخه‌ای را که دیگران بر اساس آن کار می‌کنند rebase
کرد.

## سؤال ۲: انتخاب بخشی از تغییرات (`hunk`)

یک **hunk** بخشی از خروجی `diff` است که تغییرات یک محدوده از فایل را
نشان می‌دهد. با دستور زیر می‌توان تغییرات فایل را به‌صورت تعاملی بررسی کرد
و فقط بخش‌های لازم را وارد staging کرد:

``` bash
git add -p README.md
```

برای هر بخش، گزینه‌های اصلی عبارت‌اند از:

-   `y`: افزودن این بخش به staging
-   `n`: ردکردن این بخش
-   `s`: تقسیم بخش به قسمت‌های کوچک‌تر، اگر امکان‌پذیر باشد
-   `e`: ویرایش دستی patch، در صورت نیاز و آشنایی با قالب آن
-   `q`: خروج از حالت تعاملی

در پایان می‌توان نتیجه را بررسی کرد:

``` bash
git diff --staged
git status
```

این روش کمک می‌کند هر کامیت فقط تغییرات مرتبط و منسجم را در بر بگیرد؛ در
نتیجه بازبینی، یافتن علت خطا و بازگرداندن تغییرات در آینده آسان‌تر می‌شود.

## سؤال ۳: یافتن منشأ خطا با `git bisect`

`git bisect` با جست‌وجوی دودویی در تاریخچه، کامیت واردکنندهٔ خطا را پیدا
می‌کند. ابتدا یک کامیت سالم و یک کامیت معیوب مشخص می‌کنیم:

``` bash
git bisect start
git bisect bad                 
git bisect good <good-commit>  
```

Git کامیتی میانی را checkout می‌کند. آن نسخه را آزمایش می‌کنیم و نتیجه را
اعلام می‌کنیم:

``` bash
git bisect good 
git bisect bad  
```

این روند تا شناسایی کامیت مسئول ادامه می‌یابد. سپس جست‌وجو را پایان
می‌دهیم:

``` bash
git bisect reset
```

**مثال:** اگر برنامه تا کامیت `a1b2c3` درست کار می‌کرده اما در نسخهٔ فعلی
خطا دارد، با آزمایش نسخه‌های میانی می‌توان کامیتی را که خطا را وارد کرده
پیدا کرد. چون در هر مرحله نیمی از بازه کنار گذاشته می‌شود، معمولاً به
آزمایش‌های بسیار کمتری از بررسی تک‌تک کامیت‌ها نیاز است.

## سؤال ۴: بررسی تغییرات پیش از کامیت

### ۴.۱. مشاهدهٔ تغییرات

``` bash
git status
git diff
git diff --staged
```

-   `git status` وضعیت کلی فایل‌ها و staging را نشان می‌دهد.
-   `git diff` تغییرات ثبت‌نشده در staging را نسبت به نسخهٔ staged نشان
    می‌دهد.
-   `git diff --staged` تغییراتی را نشان می‌دهد که برای کامیت بعدی آماده
    شده‌اند؛ این تغییرات با آخرین کامیت مقایسه می‌شوند.

در سناریوی سؤال، ویرایش دوم `README.md` پس از staging انجام شده است؛
بنابراین نسخهٔ staged و نسخهٔ فعلی فایل با هم تفاوت دارند.

### ۴.۲. اگر اکنون کامیت کنیم چه می‌شود؟

با یک کامیت معمولی و بدون `-a`، فقط تغییرات موجود در staging ثبت می‌شوند.
پس تغییراتی که قبلاً به staging اضافه شده‌اند وارد کامیت می‌شوند، اما
ویرایش دوم `README.md` که پس از آن انجام شده و دوباره stage نشده است،
باقی می‌ماند. فایل‌های untracked داخل `tmp/` نیز خودکار وارد کامیت
نمی‌شوند.

### ۴.۳. نادیده‌گرفتن پوشهٔ `tmp/`

در فایل `.gitignore` در ریشهٔ مخزن این الگو را اضافه می‌کنیم:

``` gitignore
/tmp/
```

این الگو فایل‌های پوشهٔ `tmp/` در ریشهٔ مخزن را از شناسایی به‌عنوان فایل‌های
جدیدِ قابل‌افزودن کنار می‌گذارد. اما `.gitignore` به‌تنهایی فایل‌هایی را که
قبلاً tracked شده‌اند از پیگیری خارج نمی‌کند؛ برای چنین فایل‌هایی باید
جداگانه از `git rm --cached` استفاده کرد. در صورت نیاز، مسیر دقیق را
بررسی کنید تا فایل‌های محلی حذف نشوند.

## سؤال ۵: رفع `merge conflict` در کار گروهی

### ۵.۱. چرا تعارض رخ داده است؟

تعارض رخ داده چون هر دو شاخه، یک بخش هم‌پوشان از `README.md` را به شکل
متفاوت تغییر داده‌اند و Git نمی‌تواند خودکار تصمیم بگیرد کدام متن نهایی
درست است. هر تغییر هم‌زمانی الزاماً conflict ایجاد نمی‌کند؛ تغییرات در
بخش‌های جدا از هم اغلب خودکار ادغام می‌شوند.

### ۵.۲. شناسایی فایل و نسخه‌های متعارض

``` bash
git status
```

این دستور فایل‌های دارای تعارض را مشخص می‌کند. در فایل، نشانگرها معمولاً به
این شکل‌اند:

``` text
<<<<<<< HEAD
متن شاخهٔ مقصد
=======
متن شاخهٔ ورودی
>>>>>>> feature-description
```

بخش بین `<<<<<<<` و `=======` نسخهٔ شاخهٔ فعلی است و بخش بین `=======` و
`>>>>>>>` نسخهٔ شاخهٔ ورودی را نشان می‌دهد. نام‌ها بسته به جهت ادغام ممکن
است متفاوت باشند.

### ۵.۳. حفظ اطلاعات هر دو تغییر و تکمیل ادغام

1.  فایل `README.md` را باز می‌کنیم و متن نهایی‌ای می‌سازیم که اطلاعات هر
    دو تغییر را حفظ کند؛ صرفاً لازم نیست یکی از دو نسخه را انتخاب کنیم.
2.  نشانگرهای تعارض را حذف می‌کنیم و متن را از نظر معنا و قالب بررسی
    می‌کنیم.
3.  تغییرات را بررسی و فایل را stage می‌کنیم:

``` bash
git diff
git add README.md
git diff --staged
git status
```

4.  پس از اطمینان از درستی متن و نبودن نشانگرها، ادغام را کامل می‌کنیم:

``` bash
git commit
```

برای اطمینان، فایل را جست‌وجو و بازبینی می‌کنیم تا رشته‌های `<<<<<<<`،
`=======` و `>>>>>>>` در متن نهایی باقی نمانده باشند. همچنین باید
آزمون‌ها یا بررسی‌های مربوط به پروژه را اجرا کرد، اگر وجود دارند.

### ۵.۴. لغو ادغام در حال انجام

اگر تصمیم بگیریم فعلاً ادغام انجام نشود و هنوز در وضعیت merge باشیم،
دستور زیر عملیات ادغام را لغو می‌کند و مخزن را به وضعیت پیش از شروع merge
برمی‌گرداند:

``` bash
git merge --abort
```

## سؤال ۶: انتخاب روش مناسب برای بازگرداندن تغییرات

### ۶.۱. تغییر ثبت‌نشده و unstaged در `notes.txt`

چون فقط می‌خواهیم تغییرات همین فایل کنار گذاشته شود و نسخهٔ staging با
آخرین کامیت برابر است، اجرا می‌کنیم:

``` bash
git restore -- notes.txt
```

این دستور تغییرات فایل در working tree را با نسخهٔ staging جایگزین می‌کند.
تغییرات ثبت‌نشدهٔ همان فایل از بین می‌روند؛ بنابراین باید پیش از اجرا مطمئن
باشیم که به آن‌ها نیاز نداریم. فایل‌های دیگر دست‌نخورده می‌مانند.

### ۶.۲. خارج‌کردن تغییرات از staging، بدون حذف ویرایش‌ها

``` bash
git restore --staged -- notes.txt
```

این دستور فایل را از staging خارج می‌کند، اما محتوای ویرایش‌شده را در
working tree نگه می‌دارد. به این ترتیب، تغییرات برای کامیت آماده نیستند
ولی از بین هم نمی‌روند.

### ۶.۳. برگرداندن یک کامیت اشتباه که به شاخهٔ مشترک push شده است

روش مناسب `git revert` است:

``` bash
git revert <commit-hash>
git push
```

این دستور یک کامیت جدید می‌سازد که اثر کامیت اشتباه را معکوس می‌کند؛ کامیت
اصلی در تاریخچه باقی می‌ماند. حذف کامیت از تاریخچه یا استفاده از
`push --force` مناسب نیست، چون هم‌تیمی‌ها کامیت قبلی را دریافت کرده‌اند و
بازنویسی تاریخچه می‌تواند تاریخچهٔ محلی آن‌ها را با مخزن مشترک ناسازگار
کند.
