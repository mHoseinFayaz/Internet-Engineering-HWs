# پاسخ تمرین HTTP


## سؤال ۱ — نسخه‌های HTTP 

- **HTTP/0.9:** نسخه‌ای بسیار ساده؛ فقط درخواست `GET`، بدون header، status code یا پشتیبانی استاندارد از انواع محتوا.
- **HTTP/1.0:** افزودن headerهای درخواست و پاسخ، status codeها و روش‌هایی مانند `POST`؛ معمولاً برای هر درخواست یک اتصال TCP جداگانه ایجاد می‌شد.
- **HTTP/1.1:** اتصال‌های پایدار (persistent connections)، header `Host` برای میزبانی چند دامنه روی یک IP، انتقال chunked و بهبودهای cache و content negotiation.
- **HTTP/2:** قالب‌بندی دودویی پیام‌ها، multiplexing چند جریان روی یک اتصال TCP و فشرده‌سازی headerها؛ هدف اصلی افزایش کارایی و کاهش تأخیر بود.
- **HTTP/3:** استفاده از QUIC به‌جای TCP؛ QUIC روی UDP اجرا می‌شود و جریان‌های مستقل دارد، بنابراین از مسدود شدن همهٔ جریان‌ها به‌علت از دست رفتن بسته در یک جریان جلوگیری می‌کند. معنا و روش‌های اصلی HTTP تا حد زیادی با نسخه‌های قبلی سازگار مانده‌اند.

**چرا HTTP/3 از UDP استفاده می‌کند؟**  
HTTP/3 مستقیماً به قابلیت اطمینان خام UDP تکیه نمی‌کند؛ QUIC قابلیت‌هایی مانند بازیابی بسته‌های ازدست‌رفته، رمزنگاری و جریان‌های چندگانه را روی UDP فراهم می‌کند. این طراحی اجازه می‌دهد اختلال در یک جریان، مانند TCP، لزوماً همهٔ جریان‌های دیگر را متوقف نکند و برقراری اتصال نیز بتواند سریع‌تر باشد.

## سؤال ۲ — ارتباط‌های stateless و stateful 

### الف) تفاوت این دو دسته

در ارتباط **stateless**، هر درخواست مستقل پردازش می‌شود و سرور برای تفسیر درخواست فعلی به حافظه‌داشتن وضعیت درخواست قبلی وابسته نیست. در ارتباط **stateful**، بخشی از وضعیت تعامل بین درخواست‌ها نگه‌داری می‌شود؛ برای نمونه، سرور می‌تواند وضعیت ورود کاربر یا محتوای سبد خرید را در طول یک نشست حفظ کند.

### ب) HTTP در کدام دسته است و چگونه مشکل را حل می‌کند؟

HTTP ذاتاً **stateless** است؛ یعنی هر درخواست باید اطلاعات لازم برای پردازش خود را داشته باشد. برای ساختن تجربه‌ای stateful روی HTTP، برنامه‌ها از روش‌هایی مانند **cookie و session** استفاده می‌کنند: سرور یک شناسهٔ نشست ایجاد می‌کند و مرورگر آن را در درخواست‌های بعدی می‌فرستد؛ سرور با استفاده از آن شناسه وضعیت مربوط به کاربر را پیدا می‌کند. روش‌هایی مانند token نیز می‌توانند اطلاعات احراز هویت را بین درخواست‌ها منتقل کنند.

## سؤال ۳ — محدودیت client/server و ارتباط دوطرفه 

### الف) شرح چالش

در مدل معمول HTTP، کلاینت درخواست را آغاز می‌کند و سرور پاسخ می‌دهد. اگر سرور بخواهد بدون دریافت درخواست تازه از کلاینت، رویدادی را به او اطلاع دهد، این الگو به‌تنهایی مناسب نیست؛ در نتیجه، پیاده‌سازی اعلان‌های لحظه‌ای، چت و دریافت رخدادهای webhook می‌تواند به سازوکارهای تکمیلی نیاز داشته باشد. در webhook، برای نمونه، یک سرویس هنگام وقوع رویداد باید بتواند به نشانی سرویس دیگر درخواست بفرستد؛ بنابراین دریافت‌کننده باید نشانی قابل‌دسترسی و endpoint مناسب فراهم کند.

### ب) راهکارهای ممکن

**WebSocket:** پس از یک handshake روی HTTP، اتصال به کانالی پایدار و دوطرفه تبدیل می‌شود. کلاینت و سرور می‌توانند هر دو در هر زمان پیام بفرستند؛ بنابراین برای چت و تعامل بلادرنگ مناسب است. در مقابل، مدیریت اتصال‌های طولانی‌مدت و مقیاس‌پذیری آن به منابع و طراحی سرور نیاز دارد.

**Server-Sent Events (SSE):** کلاینت یک درخواست HTTP برقرار می‌کند و سرور از طریق پاسخ باز، رویدادها را به‌صورت جریانی برای کلاینت می‌فرستد. این روش برای اعلان‌ها و به‌روزرسانی‌هایی مناسب است که فقط به جریان اطلاعات از سرور به کلاینت نیاز دارند؛ اما برای پیام‌های کلاینت به سرور باید درخواست HTTP جداگانه فرستاده شود.

**Long polling:** کلاینت درخواست می‌فرستد و سرور پاسخ را تا زمان آماده‌شدن داده یا پایان مهلت نگه می‌دارد. پس از دریافت پاسخ، کلاینت بلافاصله درخواست دیگری می‌فرستد. این روش بدون پروتکل تازه‌ای امکان دریافت نسبتاً به‌موقع رویدادها را می‌دهد، ولی درخواست‌های مکرر و سربار اتصال می‌توانند هزینه‌زا باشند.

**Webhook:** برای اطلاع‌رسانی بین دو سرویس، سرویس تولیدکنندهٔ رویداد به endpoint ثبت‌شدهٔ سرویس دریافت‌کننده درخواست HTTP می‌فرستد. این روش برای رویدادهای سرویس‌به‌سرویس مناسب است و معمولاً به endpoint عمومی یا قابل‌دسترسی، اعتبارسنجی درخواست‌ها و سازوکار retry نیاز دارد. برخلاف WebSocket، webhook معمولاً یک اتصال تعاملی دائمی نیست؛ بلکه درخواست‌هایی جداگانه هنگام وقوع رویداد ارسال می‌کند.

## سؤال ۴ — اجزای URL 

URL داده‌شده:

```text
ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1
```

| جزء | مقدار | توضیح |
|---|---|---|
| Scheme | `ss` | طرح یا نوع URI؛ در این مثال نشان‌دهندهٔ قالب Shadowsocks است. |
| User information | `asghar:1234!!` | اطلاعات کاربری پیش از علامت `@`؛ بخش پیش از `:` نام کاربری و بخش پس از آن رمز/اطلاعات محرمانه است. |
| Host | `ss.myproxy.com` | نام میزبان سرور |
| Port | `1234` | شمارهٔ پورت |
| Fragment | `shadowSocks1` | شناسه یا برچسب پس از `#`؛ معمولاً برای تفسیر سمت کلاینت است و به‌عنوان fragment در درخواست HTTP به سرور ارسال نمی‌شود. |
| Path / Query | وجود ندارد | در URL ارائه‌شده مسیر و query مشخص نشده‌اند. |

## سؤال ۵ — انتخاب HTTP status code در REST API 

کدهای زیر انتخاب‌های مناسب برای سناریوهای مطرح‌شده‌اند. در برخی موارد، بسته به جزئیات طراحی API، گزینه‌های دیگری هم ممکن است قابل‌دفاع باشند.

1. **مشکل پایگاه داده و انجام‌نشدن درخواست‌های login:** `503 Service Unavailable` اگر سرویس موقتاً به‌دلیل خرابی وابستگی یا نگه‌داری قادر به پاسخ‌گویی نیست. اگر خطا ناشناخته و عمومی باشد، `500 Internal Server Error` نیز مناسب است.
2. **نام کاربری واردشده وجود ندارد و login ناموفق است:** `401 Unauthorized` برای احراز هویت ناموفق. اگر API بخواهد به دلایل امنیتی وجود یا نبودن حساب را افشا نکند، می‌تواند پیام و پاسخ یکسانی برای نام کاربری ناموجود و رمز اشتباه ارائه دهد.
3. **انتقال دائمی وب‌سایت به دامنه‌ای دیگر:** `301 Moved Permanently` برای تغییر دائمی URL. برای انتقال دائمی‌ای که باید روش HTTP درخواست حفظ شود، `308 Permanent Redirect` نیز مناسب است.
4. **بیشتر بودن تعداد درخواست‌های کاربر از حد مجاز:** `429 Too Many Requests`؛ سرور می‌تواند در صورت نیاز headerی مانند `Retry-After` را نیز برگرداند.
5. **تمدید موفق JWT و بازگرداندن توکن جدید در header:** `200 OK`، چون درخواست با موفقیت انجام شده و پاسخ می‌تواند شامل اطلاعات لازم باشد. اگر عملیات موفق باشد اما بدنهٔ پاسخ عمداً خالی باشد، `204 No Content` هم می‌تواند مناسب باشد؛ البته باید مشخص باشد توکن جدید در header برگردانده می‌شود.
6. **ممنوع‌بودن دسترسی کاربر از یک بازهٔ IP:** `403 Forbidden`، چون سرور درخواست را دریافت کرده اما اجازهٔ دسترسی نمی‌دهد. این پاسخ از نظر معنایی برای منع دسترسی مناسب است؛ جزئیات پیاده‌سازی ممکن است متفاوت باشد.

**مرجع کدهای وضعیت HTTP:** [MDN — HTTP response status codes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status)

## سؤال ۶ — انواع پراکسی 

1. **استفاده از سرورهای داخلی دانشگاه برای دریافت بسته‌ها به‌جای سرورهای مرکزی:** **Forward proxy / cache proxy** یا mirror cache. سرور داخلی درخواست‌های خروجی کاربران را واسطه‌گری می‌کند و می‌تواند بسته‌ها را ذخیره کند تا دریافت‌های بعدی سریع‌تر شوند و ترافیک اینترنت کاهش یابد. در عمل، mirror مخزن بسته‌ها نیز می‌تواند همین هدف را بدون پراکسی‌کردن همهٔ درخواست‌ها محقق کند.
2. **تقسیم درخواست‌ها بر اساس مبدأ جغرافیایی درخواست:** **GeoDNS یا پراکسی معکوس/سامانهٔ توزیع بار مبتنی بر موقعیت جغرافیایی**. در این سناریو، معمولاً درخواست کاربر به نزدیک‌ترین یا مناسب‌ترین نقطهٔ خدمت‌دهی هدایت می‌شود؛ اگر منظور از پراکسی، واسطه‌ای جلوی سرورهای backend باشد، پراکسی معکوس می‌تواند درخواست را بر اساس موقعیت یا سیاست مسیریابی به backend مناسب بفرستد.
3. **اضافه‌کردن احراز هویت به یک سرویس بسیار قدیمی:** **Reverse proxy** به‌عنوان دروازهٔ احراز هویت. پراکسی معکوس پیش از رسیدن درخواست به سرویس قدیمی، هویت کاربر را بررسی می‌کند و فقط درخواست‌های مجاز را عبور می‌دهد؛ به این ترتیب معمولاً لازم نیست خود سرویس قدیمی تغییر کند.
